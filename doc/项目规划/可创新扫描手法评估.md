# 屋勘 HouseRecon — 可创新扫描手法可行性评估

> **文档版本**：v1.0
> **日期**：2026-10-04
> **目的**：找出"技术上真能做、且现有工具没做好"的扫描手法
> **诚实声明**：本文对每个想法标注**创新度**（含"包装已知技术"的情况），不吹

---

## 前置：先说清楚什么不算创新

在给方案之前，先立三条判据。**不满足这三条的，一律不叫创新：**

| 判据 | 说明 |
|---|---|
| **J1 真盲区** | 存在一个现有主流工具**系统性看不到**的东西，不是"做得不够好"而是"根本不看" |
| **J2 可判定** | 输出的结论有客观依据，不是主观打分或 AI 猜的 |
| **J3 可落地** | 个人项目在数周内能实现，不需要自研 TCP/IP 栈或需要特殊网络位置 |

**为什么需要这三条**：安全工具的"创新"九成是把已有方法重新包装（"我用 AI 做了指纹识别"——httpx 本来就是 Wappalyzer 规则匹配）。自己给自己贴金很容易，写进方案里被评委一问就穿。

# 想法 1：QUIC / UDP-443 探活 ⭐⭐⭐⭐⭐

**创新度：技法本身已知（评分 3/5），系统性整合与报告无人做（评分 5/5）**
**总评：值得做，且是唯一一个能说"主流工具系统性缺失"的点**

## 原理

2026 年最大的扫描盲区。你的调研报告已经写明：

> 绝大多数端口扫描器**根本不看 UDP/443**。一个只开放 HTTP/3 的服务，TCP/443 关闭，扫描器报 "filtered"，你完全看不到它。

**为什么 UDP 一直测不准**：UDP 无响应 = 无法区分 open 与 filtered。这是所有 UDP 扫描器的原罪。

**但 QUIC 打破了这个死结。** 关键在 QUIC 的长包头结构（RFC 9000）：

```
┌─────────────────────────────────────────────────┐
│ QUIC Long Header（明文，不加密）                  │
├─────────────────────────────────────────────────┤
│ 1 bit   Header Form  = 1 （1=长包头）            │
│ 1 bit   Fixed Bit    = 1                          │
│ 2 bit   Long Packet Type = 00 (Initial)         │
│ 4 bit   Type-Specific Bits                      │
│ 32 bit  Version  ← ⭐ 纯明文                    │
│ 8 bit   DCID Len + DCID  ← ⭐ 纯明文            │
│ 8 bit   SCID Len + SCID  ← ⭐ 纯明文            │
│ ...    Token Len / Token / Length                │
├─────────────────────────────────────────────────┤
│ Payload（加密）← CRYPTO frame 里的 ClientHello   │
└─────────────────────────────────────────────────┘
```

**探测手法**：发一个带 **保留/greased version 号**（如 `0x0a0a0a0a`）的 Initial 包。服务器解析长包头，发现版本不支持，**必须**回一个 Version Negotiation 包（Version 字段 = `0x00000000` + 它的支持版本列表）。

**为什么这个判定是确定的**：
- 收到 Version Negotiation → **端口一定开着，且一定跑 QUIC**（J2 ✅）
- 什么都没收到 → 可能是 filtered，也可能是不响应。**这一侧仍然是模糊的**，但这是唯一能把"确定开"从"可能开"里分离出来的方法
- ⭐ **不需要任何加密计算**（Initial 包的初始密钥是公开的 salt 派生，但 Version Negotiation 在解密之前就发了）

## 现有工具做到什么程度（诚实核验）

| 工具 | 支持情况 | 局限 |
|---|---|---|
| **Nmap** | ⚠️ 有 `nmap -sU -p 443 --script quic-info` | ① **需要 root**（`-sU`）② 是 Lua NSE 脚本，不是原生 ③ **nmap 是 NPSL 授权，不能嵌入** |
| **naabu** | ❌ 只扫 TCP | 完全没有 UDP 概念 |
| **httpx** | ❌ | 只有 HTTP/2，无 HTTP/3 探测 |
| **ZMap / masscan** | ❌ | 纯 TCP 单包扫描架构 |
| **nuclei** | ⚠️ 有 CVE-2026-62815 的 UDP 模板 | 单点漏洞检查，不是资产发现 |

**真实空缺**：**没有任何 Go 语言的开源资产测绘工具做这件事**。PD 套件（3 万 star 的事实标准）完全空白。

## 为什么"整合"本身就是创新

技法是已知的，但**没有人把它做成"资产发现的一等公民"**。可以做的：

```bash
wukan quic 93.184.216.34                    # 单 IP 探 QUIC
wukan quic -f hosts.txt -o quic_open.txt    # 批量
wukan recon example.com --quic              # 挂进主流程
```

**输出的核心价值 —— 这才是创新点**：

```
example.com 资产报告
├─ TCP 探测：443/tcp  →  filtered（看起来是关的）
└─ UDP 探测：443/udp  →  ⭐ QUIC 存活，Version 0x00000001
   └─ ⚠️ 该站点只提供 HTTP/3，TCP/443 关闭
   └─ ⚠️ 所有 TCP-only 扫描器（含 Shodan/Censys/naabu）都会漏掉这一条
   └─ Alt-Svc 头：h3=":443"  ✅ 声明与实际一致
```

> ⭐ **"只开放 QUIC 的服务"在 Shodan/Censys 上是不可见的**。你把它找出来并明确报出来"这是 TCP 扫描器的系统性盲区命中"—— 这个结论是有客观依据的（J2 ✅），且对防守方有直接价值（他们此前不知道自己有这个暴露面）。

## 实现难度

| 项 | 评估 |
|---|---|
| 协议复杂度 | ⭐⭐ 低。只需拼 20 字节 + 收包，不需要完整 QUIC 实现 |
| 是否需要 root | ⭐⭐ **不需要**。普通 UDP socket 即可（不需要 raw socket） |
| Go 库 | ⭐⭐ 不需要库。`net.Dial("udp", ...)` + 手工解析回包首字节 |
| 代码量 | ⭐⭐⭐ 约 150-250 行 |
| 单点风险 | ⚠️ UDP 在部分网络被 QoS 降级/丢弃，**false negative 率需实测** |

**结论：难度最低、创新点最硬。强烈建议第一个做。**

# 想法 2：指纹冲突矩阵（不是拼接指纹，是检测矛盾）⭐⭐⭐⭐

**创新度：真创新（4/5）。思路未见主流工具实现**
**总评：成本极低，洞察力强，最适合当"特色功能"**

## 原理

现有工具的所有指纹功能，本质都是**把多个识别结果拼在一起输出**：

```
Server: nginx/1.24.0
Tech: PHP/8.2, MySQL
Framework: Laravel 10
Favicon hash: -1965184550
JARM: 29d3fd00029d29d21c42d43d00041d4689a210907f1f8f0c5b8a7e1e0e1c0f2
```

**但没人做的是：检测这些结果之间的矛盾。**

## 三个真实可判定的冲突场景

### 场景 A：favicon 说 Grafana，HTTP 头说 Apache

```
favicon hash:  -1965184550  →  Grafana
Server:        Apache/2.4.52
Title:         Apache2 Ubuntu Default Page
```

**结论**：要么 Grafana 在反向代理后面（Apache 代理 Grafana），**要么你的指纹库错了**。

⚠️ 报告里的原话：**favicon hash 的误报是结构性的，不是模型精度问题** —— favicon 只有几百字节，不同应用共用同一图标必然碰撞。**所以"favicon 说是 X 但 HTTP 说 Y"这个矛盾，是确定性的、值得报告的。**

### 场景 B：CDN 声称 + 源站特征泄露

```
Server:         cloudflare
CF-RAY:         8d0e0a1b2c3d4e5f
X-Powered-By:   PHP/7.4.33           ← ⚠️ 源站特征泄露
X-Cache:        MISS
Set-Cookie:     PHPSESSID=...        ← ⚠️ 会话未加 secure/httponly
```

**Cloudflare 会缓存和隐藏源站特征，但 PHP 的 X-Powered-By 和 PHPSESSID Cookie 会穿透**。这是 CDN 后面源站的**信息泄露**。

### 场景 C：JARM 说 OpenSSL 1.1.1，但 Server 头说 nginx 1.25

```
JARM:      29d3fd00029d29d21c42d43d00041d46...
           → OpenSSL 1.1.1 系（该指纹在 OpenSSL 1.1.1 上稳定）
Server:    nginx/1.25.3            → 官方编译应带 OpenSSL 3.x
```

**结论**：要么 Server 头是伪造的（安全加固/误导），要么中间有代理改写。**两种都值得记一笔。**

## 输出形态

```bash
wukan tech -f urls.txt --conflicts
```

```
⚠️ 指纹冲突 · 93.184.216.34:443
├─ 冲突类型：代理穿透
│    favicon 判定 = Grafana (hash -1965184550)
│    Server 头    = Apache/2.4.52
│    判定         = 高度可疑。favicon 误报率结构性偏高，但两者同时冲突需人工核
├─ 冲突类型：CDN 源站特征泄露
│    CDN  = cloudflare（CF-RAY 头确认）
│    泄露 = X-Powered-By: PHP/7.4.33 / PHPSESSID 无 secure 标记
└─ 冲突类型：版本自相矛盾
     JARM 推得 OpenSSL 1.1.1 系，Server 头声明 nginx 1.25.3（应带 OpenSSL 3.x）
```

## 为什么这个真的算创新

| 现有工具 | 行为 |
|---|---|
| httpx | 输出 `tech-detect` 结果，**纯拼接，不做校验** |
| nuclei | 匹配模板，**不比对指纹之间的一致性** |
| Wappalyzer | 单点规则匹配，**不与其他源交叉** |
| Shodan / Censys | 存什么显示什么，**不推理矛盾** |

**"把多个独立来源的结论做交叉一致性检验，矛盾处降权并报出"** —— 这个逻辑我没在任何主流工具里见到实现。

## 实现难度

| 项 | 评估 |
|---|---|
| 核心逻辑 | ⭐ 极低。就是一个规则表 + 一致性判断，约 200-300 行 |
| 指纹来源 | 复用现有（Wappalyzer 数据集 + 自建 mmh3 + JARM） |
| 难点 | 在于**规则表的质量**，不在代码 |
| 收益 | ⭐⭐⭐ 每条冲突都是可行动的具体发现，不是"我扫到了 200 个站点" |

**结论：成本最低、差异化最明显的一个。**

# 想法 3：CT 日志时间序列 —— 查"曾经存在过"的域名 ⭐⭐⭐⭐

**创新度：方法真新（4/5）。现有工具只查"当前"**

## 原理

你的调研报告里那句洞察是这个想法的种子：

> **应用下线功能时常常不删除后端逻辑。** 一个 18 个月前"移除"的 `/admin/export` 端点可能仍返回 200 —— URL 只是不再被任何地方链接了。

**CT 日志是只追加的、永久公开的、按时间排序的。**

但现有 subfinder / crt.sh 查询工具全部是：**"这个域名现在有哪些 SAN"** —— 它们按域名归集，输出去重后的集合。**默认不带时间维度。**

**换个问法就是创新**：

> ❌ 现在有哪些子域名（默认问法）
> ✅ **这个域名的证书上，历史上曾经出现过哪些域名？哪些后来消失了？**

## 三个具体玩法

### 玩法 1：历史 SAN 全量导出（带时间戳）

```bash
wukan ct history example.com --since 2019
```

```
证书历史（crt.sh / CT 日志）
├─ 2026-10-01  SAN=*.example.com, example.com
├─ 2024-03-15  SAN=*.example.com, example.com, legacy.corp.example.com
├─ 2021-07-02  SAN=*.example.com, dev-internal.example.com, vpn.example.com
└─ 2019-01-08  SAN=*.example.com, old-jira.example.com, wiki-internal.example.com

⚠️ 已从证书中消失但域名可能仍可解析的（需验证）：
   dev-internal.example.com
   old-jira.example.com
   wiki-internal.example.com
```

### 玩法 2：⭐ 消失的域名 × 泛域名解析 = 高价值发现

**这是最实用的一招**：

```
泛域名配置：*.example.com → 1.2.3.4（任意子域都解析）

历史证书曾签发过 old-jira.example.com
今天 old-jira.example.com 仍然解析 → 1.2.3.4
   ↓
⚠️ 这个域名主人以为已经下线了，但它仍然可达
⚠️ 如果源站按 Host 头做虚拟主机，它可能仍返回内部内容
```

**为什么这个手法有 J1（真盲区）性质**：主动 DNS 暴力枚举会找出**所有**能解析的子域，但**无法区分"这个域名是有意部署的"还是"三年前废弃的"**。CT 时间戳提供了这个区分依据 —— 而现有工具都在丢掉这个信息。

### 玩法 3：跨证书关联（弱归属推断）

一张证书里同时出现 `a.example.com` 和 `b.othercompany.com` → **两家公司共用一张证书**（可能是同一台服务器、同一套 k8s 集群、或并购遗留）。

**能推断出资产间的物理关联** —— 这是 Maltego 卖 €3,000/年的那类"关系网"的一个具体子集，但**这个子集可以纯被动、准确率 100%（证书是客观事实）**。

## 现有工具的缺口

| 工具 | 查询方式 | 是否带时间 |
|---|---|---|
| crt.sh 网页 | 按域名搜 | ✅ 表格里有 NotBefore，但工具化程度低 |
| subfinder | 按域名聚合 | ❌ 去重后输出，**时间戳丢弃** |
| amass | 关联分析 | 🟡 有关系图但粒度粗 |
| **屋勘可以做的** | 按证书 ID 拉取完整时间线 | ✅ **输出"域名 × 首次出现 × 最后出现 × 消失标记"** |

## 实现难度

| 项 | 评估 |
|---|---|
| 数据源 | crt.sh 的 JSON API（`?q=...&output=json` 返回含 `entry_timestamp` / `not_before`） |
| 核心逻辑 | ⭐⭐ 聚合 + 时间戳对比，约 250 行 |
| 是否主动探测 | ❌ **纯被动**，零风险 |
| 难点 | crt.sh 经常限流/超时，需要重试和缓存 |
| **最大价值** | ⭐⭐⭐⭐ **玩法 2 能直接找出"以为下线但仍可达"的资产** |

**结论：零法律风险 + 有客观判据 + 直接产出可行动发现。这个应该做。**

# 想法 4：悬垂资源接管指纹库（自动确认，不是只列 CNAME）⭐⭐⭐⭐

**创新度：模式已知（subfinder/社区脚本都有），但**自动化确认**做得差（2/5）**

## 原理

**现有工具的做法**：找出所有指向第三方服务的 CNAME，输出一个列表，**人肉看**。

```bash
# 现有工具的输出
dev.example.com  CNAME  dev-site.herokuapp.com
old.example.com  CNAME  old-bucket.s3.amazonaws.com
```

**然后就没了。** 你还是得一个个去访问、判断是不是真的能接管。

**能不能自动判断？** 能。因为**每个平台的"资源不存在"有各自特征鲜明的响应**：

| 平台 | 悬垂时的典型响应 | 可判定特征 |
|---|---|---|
| **Heroku** | `No such app` | 精确文案匹配 |
| **GitHub Pages** | HTTP 404 + `There isn't a GitHub Pages site here.` | 文案 + 404 |
| **AWS S3** | `NoSuchBucket` / `The specified bucket does not exist` | XML 错误码 |
| **Azure Blob** | `The specified blob does not exist.` + `BlobNotFound` | XML 错误码 |
| **Cloudflare R2** | 类似 S3 | XML 错误码 |
| **Fastly** | `Fastly error: unknown domain` | 特定 header |
| **Shopify** | `Sorry, this shop is currently unavailable.` | 文案 |
| **Pantheon** | `The gods are wise, but do not know of the site which you seek.` | 文案（著名的耍嘴皮子） |
| **Telegram** | 空白页 | 弱特征 |
| **Zendesk** | `Help Center Closed` | 文案 |

**判定逻辑**：

```
① CNAME 目标在已知平台列表
② 该平台在"资源不存在"时的特征库
③ 主动 GET 一次（需授权）
④ 命中特征 → ⚠️ 高危悬垂，可被任何人注册接管
⑤ 未命中 → 资源存在，非悬垂
```

## 为什么值得做

| 现有工具 | 自动化程度 |
|---|---|
| subfinder | 只找 CNAME，不判断悬垂 |
| nuclei 模板 | 有 takeover 模板，但**一个模板对一个平台**，十几个平台要十几个模板 |
| 社区脚本 | 有 `takeover.py` 之类，但**都是人工逐个看** |
| **屋勘** | ⭐ 一个指纹表 + 一个判定循环，**一次跑完十几个平台** |

**"接管风险"是 CT/被动 DNS 分析中严重性最高的发现** —— 有来源明确说：

> Dangling CNAME records 是 CT 和被动 DNS 分析中**严重性最高的发现**。CNAME 指向已下线云资源，任何攻击者注册同名资源即可接管。

## 实现难度

| 项 | 评估 |
|---|---|
| CNAME 提取 | ⭐⭐ 现成的（dnsx 或 miekg/dns） |
| 平台指纹库 | ⭐⭐ 手工整理约 15 个平台，每个 1-2 个特征，约 200 行数据 |
| 判定循环 | ⭐⭐⭐ 约 150 行 |
| 是否需授权 | 🔴 **需要**（要发 HTTP 请求验证） |
| 收益 | ⭐⭐⭐⭐ 直接可行动：删掉 CNAME 记录即可修复 |

**结论：模式不新，但自动化有明显缺口，且能做出可行动结论。中优先级。**

# 想法 5：Alt-Svc 声明与实际能力不符（配置漂移检测）⭐⭐⭐

**创新度：真小众（3/5）。几乎没人做，但极便宜**

## 原理

**RFC 9460** 定义了 `Alt-Svc` 响应头，浏览器靠它知道"这个站点支持 HTTP/3"：

```
Alt-Svc: h3=":443"; ma=86400
```

**但这个头是服务端自己声明的，可能说谎。** 三种不一致：

| 场景 | Alt-Svc 声明 | UDP/443 实际 | 判定 |
|---|---|---|---|
| **说谎** | `h3=":443"` | filtered | ⚠️ 配置错误或中间设备阻断，浏览器会先尝试 QUIC 然后回退，**增加首字节延迟** |
| **过度保守** | 无 Alt-Svc | QUIC 存活 | 🟡 服务端配置漏了，**能力没被利用**（性能损失） |
| **宣告未部署** | `h3=":443"` | QUIC 存活但版本不支持 | ⚠️ 版本不匹配 |
| 正常 | `h3` | QUIC 存活 | ✅ |

**"QUIC 探活 + Alt-Svc 头解析"这两个数据源一对比，就得出配置是否正确。**

## 为什么这不是纯玩具

- **安全侧**：Alt-Svc 声明了但端口不通，说明**网络边界有东西在静默阻断 UDP** —— 这本身是个配置缺陷，会让所有 QUIC 保护失效
- **性能侧**：漏配 Alt-Svc = 白白浪费 HTTP/3 的 0-RTT 优势

## 实现难度

| 项 | 评估 |
|---|---|
| 实现 | ⭐ 极低。HTTP 响应头解析 + 复用想法 1 的 QUIC 探活结果，约 80 行 |
| 收益 | 🟡 中等。属于"发现问题但不紧急" |
| 独特性 | ⭐⭐⭐ 几乎没人做这个对比 |

**结论：便宜，可以作为想法 1 的附赠功能，不单独立项。**

# 我不推荐的方向（以及为什么）

这几个是你可能想到但我建议放弃的：

| 方向 | 为什么放弃 |
|---|---|
| **AI 指纹识别** | ⛔ 报告已查证：不存在可信基准，httpx 本身就是 Wappalyzer 规则匹配。favicon 碰撞是**哈希的数学性质**，换 ML 消不掉（除非你维护样本库，样本库会腐化） |
| **自研无状态全网扫描** | ⛔ ZMap 已 Apache-2.0 + v4.4.0 活跃。国内判例明确：扫描本身即被认定为"侵入"的实施行为。**技术上和法律上都不划算** |
| **eBPF/XDP 加速扫描** | ⛔ 报告已核验：**没有任何主流资产测绘工具采用 eBPF/XDP 做扫描加速**。技术上也说不通——eBPF 的优势是"对本机每个进来的包做快速决策"，而扫描器的工作是"向 42.9 亿个地址各发一个包"，瓶颈在发包侧吞吐与网卡 DMA 效率 |
| **引入 LLM 做实体识别** | ⛔ 学术实测：**比专用基线低 25%**。视觉核验 280 问只对 14 个。定位应该是"去重/分组/排序的噪声削减器"，不是发现器 |
| **SMTP 邮箱验证** | ⛔ 报告的禁止性建议原文："**不要为了'验证一下'而跑 SMTP 枚举。这条线的法律风险收益比极差**" |

# 技术前提核验记录

**QUIC 探测（想法 1）已核验的协议事实**（来源 RFC 9000 / draft-ietf-quic-transport）：

| 事实 | 值 | 用途 |
|---|---|---|
| 长包头首字节 | Header Form=1, Fixed Bit=1, Type=00(Initial) | 判定是 QUIC 长包头 |
| Version 字段 | 偏移 1-4，32bit，**明文** | 探测 greased version |
| DCID Len | 偏移 5，8bit，v1 规定 **MUST NOT exceed 20** | 解析用 |
| Version Negotiation 触发 | 版本不支持时，**在解密之前**就回包 | ⭐ 无需加密计算 |
| VN 包的 Version 字段 | **固定 0x00000000** | 确定判定标志 |
| 已知版本 | v1=`0x00000001`, v2=`0x6b3343cf` | 结果解析 |
| Initial 最小长度 | 1200 字节（含 PADDING，防放大攻击） | 构造包体 |
| 反射攻击防护 | 客户端 Initial 必须 PADDING 到 ≥1200 字节 | 构造包体 |

**JARM 主动指纹**（报告已核验）：10 个构造 ClientHello → 62 字符，前 30 字符是各 ClientHello 的密码/TLS 选择（"000"=拒绝协商），后 32 字符是累积扩展的截断 SHA256。

**favicon hash**（报告已核验）：MurmurHash3 x86_32，Base64 输入**按 RFC 2045 每 76 字符换行**，输出**有符号整数**。

# 落地建议：三个手法如何嵌进日常命令

```bash
# 想法 1 + 5：QUIC 探活 + Alt-Svc 一致性（挂进 recon）
$ wukan recon example.com --quic
  ✅ DNS / WHOIS / 证书 / 子域 / IP归属
  ✅ TCP 端口
  ⭐ UDP/443 QUIC 探活           ← 新增
  ⭐ Alt-Svc 声明 vs 实际一致性    ← 新增

# 想法 2：指纹冲突
$ wukan tech -f urls.txt --conflicts
  ✅ 技术栈识别
  ⭐ 指纹交叉一致性检验 + 矛盾降权  ← 新增

# 想法 3：CT 时间序列
$ wukan ct history example.com --since 2019
  ⭐ 证书 SAN 历史时间线
  ⭐ 消失域名 × 当前解析 = 疑似遗留资产
```

**三个手法的共同点：都输出有客观依据的结论（J2），都挂在已有流程上（不增加使用负担），都有明确"现有工具做不到"的点（J1）。**

## 一句话收尾

> **不要造新的扫描方式，要去填现有工具系统性不看的坑。**
>
> 最硬的一个坑：**QUIC 只开放的服务，Shodan / Censys / naabu / httpx / ZMap 全部看不见**（Nmap 有个 Lua 脚本但要 root，且 NPSL 不能嵌入）。
>
> 最便宜的一个坑：**指纹之间互相矛盾这件事，没有任何工具在检查。**
>
> 最被浪费的一个坑：**CT 日志的时间戳被所有现有工具丢掉了**，而它恰好能区分"有意部署"和"三年前就废弃但还能解析"。

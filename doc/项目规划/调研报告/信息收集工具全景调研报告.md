# 第一部分：先看结论

## 1.1 调研过程中推翻的 7 个常见误解

这轮调研最有价值的产出不是工具列表，而是**以下这些广泛流传但已被证伪或过时的说法**。如果你之前的选型文档里有这些内容，建议立刻修正。

| # | 常见说法 | 实际情况 | 影响 |
|---|---|---|---|
| 1 | "Censys 靠 ZMap 扫全网" | **已过期**。Censys 官方文档把 ZMap 归入 "Deprecated IPv4 Scans"，明确说不再执行周期性扫描，仅保留历史数据。現自称 "continuous scanning engine with automatic protocol detection" | 若你在方案里写"Censys = ZMap"，评委/客户会质疑你的技术功底 |
| 2 | "naabu 的 -sV 调用 NPSL 指纹库" | **错**。naabu 根本没有 `-sV` 旗标，服务识别必须显式外挂 `-nmap-cli 'nmap -sV'`。naabu 端口扫描部分是纯 MIT | 商用集成时误判许可证风险 |
| 3 | "Shodan 的 favicon hash 是 MD5" | **错**。是 MurmurHash3 x86_32，输入按 **RFC 2045 每 76 字符换行**的 Base64，输出为**有符号整数**。官方文档没写清换行规则，是 Jorian Woltjer 用 preimage 实验反推的 | 自建工具算出的 hash 永远对不上 Shodan，中文教程普遍抄错 |
| 4 | "Quake 是绿盟的" | **错**。Quake（`quake.360.cn`）是 **360 网络安全响应中心**。绿盟对应产品线是 CTEM / TVM，不以 Quake 对外提供 | 采购沟通直接对不上人 |
| 5 | "Google 的 cache: 和 link: 还能用" | **完全失效**。`cache:` 2024 年初移除，`link:` 2017 移除，`related:` 2023 移除，`~` 2013 移除，`+` 2011 移除 | 大量教程仍在教这些，包括很多中文安全文章 |
| 6 | "AI 指纹识别准确率 85-90%" | **查证后不存在这类可信基准**。检索结果全是反欺诈/设备指纹领域的厂商营销 SEO 内容。httpx 的技术栈识别**仍是基于 Wappalyzer 的规则匹配**，favicon hash 是**确定性哈希**（零学习成分） | 写进方案里的"AI 识别率"数字基本是编的 |
| 7 | "SpiderFoot 有 37 条关联规则，能力很强" | 数字没错，但**主分支代码停在 2023-02-21，correlations/ 目录停在 2022-04-30**。这个"关联能力"实际是 2022 年的设计 | 关键能力已 3 年未更新 |

**另外两个需要澄清的名字**：Lattica 和 ByteMeAI **不是** OSINT 或代码搜索平台。查证到 Lattica 是加密货币 AI 推理市场（`ai.lattica.org`），ByteMe 是中贝通信的"数字分身"AI 产品。如果这两个名字来自你的需求文档，建议回头核实信息源。

## 1.2 十个最值得记住的结论

1. **FOFA 在国内资产测绘上强于 Shodan/Censys，原因是境内扫描节点 + 中国特色指纹库，不是营销。** 第三方对比文档的原话：*"when a target operates in China, Japan, Korea, or Southeast Asia, FOFA often surfaces hosts that Shodan and Censys miss entirely"*。

2. **最省钱的实践建议：至少用两个引擎。** 三者结果集差异巨大且失败模式不同 —— 对同一网段做两次查询取 **diff**，新出现的资产往往就是配置最粗糙的那批。这是免费获得高价值线索的最便宜方式。

3. **"AI 让 OSINT 变强了"是半真半假。** 分环节看：采集指引、海量初筛、报告起草**确实变强**；实体识别比专用基线**低 25%**；视觉核验 280 问只对了 14 个；实时信息**35% 概率重复虚假信息，拒答率从 31% 跌到接近 0**。根本原因：**LLM 让"生成"变便宜了，但没有让"验证"变便宜**。

4. **凭据泄露监控的瓶颈不在检测能力，在分诊能力和基线治理。** 噪音的本质不是工具不好，是没有基线。

5. **stealer log 里的有效 session cookie 比密码更致命** —— 改密码无效，必须吊销会话。这是凭据暴露领域最被低估的运维事实，也是商业情报平台溢价的真正理由。

6. **商业平台的溢价买的是"时间差"，不是"数据量"。** SpyCloud 卖的是 infostealer 日志比暗网论坛监控早得多这个结构性优势。Maltego 的 €3,000/年起里有相当部分是 CT 日志 + DNS 查询这类你本可以 20 行 Python 做的部分。

7. **Nmap 的许可证是商业禁用型（NPSL）。** 明确禁止嵌入商业软硬件产品（含 Docker 镜像、VM、appliance）。**仅"读取 nmap-service-probes"即被定义为衍生作品**。要商用必须买 OEM 授权。

8. **端口扫描在中国司法实践中已被明确作为犯罪行为的实施环节**，不是"未造成后果就无罪"。已有判例：董某扫描县政府信息网站获刑 9 个月；丁某因售卖爬虫工具获刑 1 年 6 缓 2 年。

9. **云上扫到的不是"主机开了什么"，是"安全组允许公网访问什么"。** 这两者永远不等价。要回答"这台机器实际开了什么"，唯一权威方法是登录主机执行 `ss -lunp`。

10. **2026 年最重要的两个盲区**：QUIC/HTTP3（UDP/443 无响应 = open|filtered，无法区分，扫描器基本看不到）和 catch-all 邮箱域（让所有 SMTP 探测结果失效）。

## 1.3 三大类工具的定位速览

| 类别 | 代表 | 核心能力 | 什么时候用 |
|---|---|---|---|
| **主动测绘** | Nmap / naabu / httpx / ZMap / masscan | 主动发包，拿到"现在"的真实状态 | 你拥有或已授权的资产 |
| **被动索引** | Shodan / Censys / FOFA / ZoomEye / Quake | 查别人已扫好的索引 | 竞品/客户面、影子资产发现 |

# 第二部分：信息收集的技术分层与边界

理解这一节比记住任何工具列表都重要。

## 2.1 五个层次

```
第5层  AI 辅助层    nuclei -llm 语义匹配、LLM 生成采集查询与报告初稿
第4层  关联分析层    Maltego 图谱 / SpiderFoot 关联规则 / 人工交叉验证
第3层  主动探测层    Nmap、naabu、httpx、ZMap、nuclei、fofax
第2层  被动索引层    Shodan、Censys、FOFA、ZoomEye、Quake、crt.sh、CT 日志
第1层  原始数据层    DNS、WHOIS、证书透明度日志、搜索引擎索引、暗网 paste
```

**上层依赖下层，但层间不能互相替代。** 关键在于理解每层能拿到什么、拿不到什么。

## 2.2 主动 vs 被动的边界（哪些数据被动拿不到）

**被动能拿到**：子域名（CT 日志、PassiveDNS、历史解析）、DNS 记录、已开放端口的**历史快照**、证书、WHOIS、搜索引擎索引过的页面。

**被动拿不到，必须主动**：

| 拿不到的东西 | 为什么 |
|---|---|
| **"现在"是否还开着** | 被动索引必然滞后。网上流传的"Censys 12.3h / Shodan 76.5h 发现新服务"无法独立验证，但滞后是结构性的 |
| **服务版本与配置** | 必须发协议握手才能拿到 banner |
| **子域解析的 IP 是否仍属于目标** | DNS rebinding、悬垂 CNAME 只能主动验证 |
| **WAF/中间件后的真实暴露面** | 被动看到的是 CDN 边缘 IP |
| **内网可达性** | 完全不可能 |
| **敏感文件、已知漏洞的实际可利用性** | nuclei 的活 |

**反向边界（容易忽略）**：主动扫描会**留下痕迹** —— 防火墙日志、IDS 告警、WAF 日志、目标侧的 `established` 记录。蓝队在生产环境做全量 SYN 扫描会触发自家安全团队告警，**这是授权流程要解决的事，不是技术问题**。

## 2.3 三个正在合拢的边界

**边界一：HTTP/3 (QUIC) 是最大的扫描盲区。**

绝大多数端口扫描器**根本不看 UDP/443**。原因是 UDP 探测天然不可靠（无响应 = open|filtered，无法区分）。结果：一个只开放 HTTP/3 的服务，TCP/443 关闭，扫描器报 "filtered"，你完全看不到它。

而 HTTP/3 部署率在快速上升 —— 浏览器通过响应里的 `Alt-Svc` 头或 DNS HTTPS 记录（RFC 9460）得知服务端支持，然后切到 QUIC。**结果是：同一个站点，TCP 探测和浏览器实际使用的协议可能完全不同。**

**连带影响**：QUIC 加密了传输层头部本身（包号、CID 轮换全在密文里），SNI 位于加密的 CRYPTO frame 内，配合 ECH 后明文里连服务器名都看不到；连接用 CID 而非四元组标识，**基于四元组的 beaconing 检测直接失效**。2026 年 8 月 Seqrite 披露的 Operation QUICSILVER（针对缅甸外交部人员的 Go 后门 QUICAgent）就是利用 UDP/443 做 C2 隐蔽信道。

**边界二：cloud 的 SYN Proxy 让端口扫描产生大规模误报。**

AWS Global Accelerator 的边缘使用无状态 SYN Proxy（SYN Cookies）抗 DDoS —— **无论端口背后有无真实服务，都会对任何 SYN 回 SYN-ACK**。只做半开 SYN 扫描的逻辑"收到 SYN-ACK ⇒ 开放"会把 21/23/179/636/3306/3389/5432/5985 全部误判为 open；而扫描器不回 ACK，SYN Proxy 也就永远不会暴露"该端口无监听"。

**验证方法**：改用完整连接扫描 `nmap -sT -sV -p <port>`，会得到 no response，即真实状态。

**推广结论**：任何采用 SYN Proxy / SYN Cookie 的 DDoS 防护（不只是 AWS）都会造成同类误报。**蓝队必须要求扫描方用 -sT/-sV 交叉验证，否则告警全是噪声。**

**边界三：Nmap 在云环境有三个高频坑。**

| 坑 | 现象 | 解法 |
|---|---|---|
| 安全组 DROP ICMP | 主机发现失败 → **直接跳过该主机的端口扫描** → 所有云主机都显示 down | `-Pn` 跳过主机发现 |
| Global Accelerator SYN Proxy | 大量端口误报 open | 用 `-sT -sV` 交叉验证 |
| 下一代防火墙 RST rate limiting | 本应 filtered 的端口被误判 closed | 交叉验证 |

**关于阿里云**：未找到权威一手资料，不做断言。

## 2.4 云上资产梳理的根本性局限（写进报告方法论章节）

从公网扫云上资产，扫到的是**安全组/网络 ACL 允许的公网入口**，不是"主机上真实监听的服务"。

**要回答"这台机器实际开了什么"，唯一权威方法是登录主机执行 `ss -lunp` / `ss -ltnp`。** 扫描给你的是"从互联网视角可达什么"，这两者永远不等价 —— 这条应写进任何资产梳理报告的方法论章节，也是评委最容易追问的点。

## 3.2 五个必须理解的工作原理

### 原理 1：TCP SYN 半开扫描（-sS）—— 不完成三次握手

发 SYN，收 SYN-ACK 判 open，收 RST 判 closed，超时判 filtered。**不完成第三次握手**，因此不占用内核 socket、不消耗目标侧连接表。

**代价**：这是它**分不清"无监听"与"被 SYN Proxy 伪装"的根本原因**（见 §2.3 边界二）。扫描速度的代价是：大量 closed/filtered 端口时，只有真过滤才超时。

### 原理 2：TCP ACK 扫描（-sA）为什么慢 —— 以及为什么它已失去价值

ACK 扫描的判定依据是"目标是否回 RST" —— **回 RST 说明端口可达（closed），不回说明被过滤（filtered）**。它无法区分 open 和 closed，因为 open 端口收到裸 ACK 时的行为取决于内核实现（多数回 RST）。

因为 `filtered` 只能靠**超时**判定（Nmap 默认 ACK 扫描设更短超时），**ACK 扫描的耗时本质上被"等待超时"支配**。

**现代网络已基本失去存在价值**：既不能发现 open 端口，又必然产生全端口流量、更易触发 IDS。社区共识是"仅用于穿透 stateless firewall 判断主机是否在线"（`-PA`）。

### 原理 3：ZMap 的无状态设计 —— 把会话状态编码进报文本身

有状态扫描的内存占用是 **O(N)**（每个未完成连接都要 socket + 定时器 + 连接跟踪表项）。ZMap 把状态**编码进报文本身** —— 用 TCP 初始序列号（ISN）承载"这是我发给哪个 IP 的"，或 ICMP identifier 承载。发包线程发完即忘，收包线程独立比对回填。**内存因此是 O(1)**。

**地址生成用 32 位 IPv4 空间的循环乘法群**：取随机原根 g，对全空间做排列，伪随机顺序恰好访问每个地址恰好一次。**这比顺序递增 IP 优越得多** —— 顺序扫描会打满相邻路由器队列并直接触发子网 IDS 告警，而群排列天然负载分散，**且统计上可证明覆盖完整**。

**性能路径**：绕过内核栈，用 PF_RING ZC（Zero Copy，直接网卡访问）+ netmap。**已知代价**：单包探测意味着单包确认，约 **2% 响应丢失**。

**masscan 的本质区别**：架构同源（自研异步 TCP/IP 栈），但**支持多端口同时扫**（ZMap 单次扫描单端口）。

### 原理 4：favicon hash 的误报是结构性的，不是模型精度问题

favicon hash 是**确定性哈希**（Shodan 风格的 mmh3 + base64 + 每 76 字符换行，输出有符号整数），**零学习成分**。

**它的误报率来源是根本性的：favicon 只有几百字节，不同应用共用同一图标（尤其是框架默认图标、CSS 框架默认 favicon）必然碰撞。** 这是哈希本身的性质，换成 ML 也不能消除 —— 除非你维护一个真实样本库，而样本库会随时间腐化。

**httpx 的技术栈识别实际是**基于 **Wappalyzer 数据集的规则匹配**，不是 ML。

### 原理 5：被动收集与 API 限速

**subfinder 是纯被动的**：只调用第三方 API/网页，**不对目标发任何包**（官方 README：*"passive model guarantees speed and stealthiness"*）。

支持 `-rls "hackertarget=10/s,shodan=15/s"` **按源分别限速** —— 这点很重要，共享 IP 批量跑极易被 CT 日志和搜索引擎风控封禁。

## 3.3 许可证（商用选型的硬约束）

| 许可证 | 工具 | 商用影响 |
|---|---|---|
| **NPSL** | Nmap | ❌ **明确禁止**嵌入商业软硬件产品，含 appliance/VM/Docker 镜像。项目方靠卖 Nmap OEM 授权盈利。**仅读取 nmap-service-probes 即被定义为衍生作品**（Gentoo 因此 license-mask，Debian 有对应 bug 讨论） |
| **AGPL-3.0** | masscan, TruffleHog | ⚠️ 网络服务传染条款。闭源 SaaS 慎用 |
| **GPL-3.0** | RustScan, XSStrike, fofax, GHunt | ⚠️ copyleft。**注意 Sliver (C2) 和 RustScan 都是 GPL-3.0**，这两个常被误认为 MIT |
| **GPL-2.0** | dnsrecon | ⚠️ 同上 |
| **Apache-2.0** | ZMap, **Amass** | ✅ 商用友好，含专利授权 |
| **MIT** | 整个 ProjectDiscovery 套件 | ✅ 最宽松 |
| **无许可证** | waybackurls | ⚠️ **无 LICENSE = 保留所有权利**，默认不可商用再分发 |

> **Amass 许可证澄清**：GitHub API 显示 NOASSERTION 是因为子组件有独立许可证。直接拉取 LICENSE 原文确认是 **Apache-2.0**（Copyright 2017 Jeff Foley），**不必因此认为它不能商用**。

**若要做商业产品**：端口扫描 + Web 指纹用 MIT 套件或 Apache-2.0 的 ZMap 是安全路径；必须用 Nmap 引擎则买 OEM。

## 3.4 真实局限与坑

**Nmap**：覆盖面最广，是**内网资产梳理的事实标准**，也是唯一能给出可信 OS 指纹的工具。缺点：慢、需 root、NPSL 污染、IDS 特征明确。2026 年 Nmap 已到 **7.991**；7.95 修了 **CVE-2026-58058**（构造的 IPv6 响应带截断扩展头会触发越界读与崩溃，扫描 IPv6 目标时注意）。

**Amass 的真实状态警示**：v5.1.1 发布于 2026-04-07，**最后推送 2026-07-19（约 2.5 个月前）**，而 v4.2.0 → v5.0.0 之间隔了**近 2 年**。项目未归档，但活跃度远低于 PD 套件。选型若看重维护密度，subfinder 更稳；Amass 优势在资产库 + OAM 建模 + 可视化。

**Amass v5 架构变化**：不再是单体命令，拆成 **9 个二进制**（`amass, oam_enum, amass_engine, ae_isready, oam_subs, oam_assoc, oam_viz, oam_track, oam_i2y`）。数据流变成"资产 → OAM 记录 → 写库 → 后续查询数据库而非重跑发现"。

**nuclei 的 AI 能力是真实存在的（但不是资产指纹）**：v3 加了 `-llm` 做语义匹配，支持 openai / ollama / llamacpp / vllm / lmstudio / groq / openrouter / together，可配 `-llm-max-calls`（默认 5000）、`-llm-concurrency`（默认 4）、`-llm-cache`。配套 commit「llm matchers and extractors on all protocols」已扩展到所有协议。**支持本地 ollama/llamacpp/vllm 是数据不出境场景的关键卖点。**

**关于 eBPF 加速扫描：没有证据。** 检索到的都是 XDP/DPDK 在流量处理与 DDoS 清洗上的数据。**没有任何主流资产测绘工具采用 eBPF/XDP 做扫描加速** —— ZMap/masscan 走的是 PF_RING ZC / netmap / DPDK。技术上也说得通：eBPF/XDP 的优势是"对本机每个进来的包做一次快速决策"，而扫描器的工作是"向 42.9 亿个地址各发一个包"，瓶颈在发包侧的批量吞吐与网卡驱动 DMA 效率。

## 3.5 选型建议

| 场景 | 推荐组合 | 理由 |
|---|---|---|
| **蓝队内网资产梳理** | Nmap（-sT）+ naabu + httpx + tlsx | MIT 覆盖，OS 指纹只有 Nmap 能给；tlsx 专精证书层 |
| **蓝队公网暴露面监控** | **uncover（FOFA+Quake+Hunter+Censys 多引擎）** + nuclei + tlsx | uncover 实测支持 14 个引擎，**国内引擎覆盖是 Shodan/Censys 补不了的** |
| **红队外部打点（授权内）** | subfinder → naabu → httpx → katana → nuclei | 全 MIT，管道化，中文资料最多 |
| **大网段端口普查** | ZMap（研究/普查）+ masscan（多端口，注意 AGPL） | ZMap 维护活跃；masscan 低维护但可用 |
| **商业产品集成** | MIT（PD 套件）+ Apache-2.0（ZMap/Amass），**避开 Nmap NPSL 与 AGPL/GPL** | NPSL 明确禁商用嵌入 |
| **数据不出境** | nuclei `-llm-provider ollama/llamacpp` + 自建 Wappalyzer 指纹 | v3 实测支持本地 LLM 端点 |

**红旗清单**：waybackurls（无许可证 + 2024-05 停更）、gospider（2024-04 停更）、XSStrike（2025-04 停更）、masscan（release 停在 2021）、detect-secrets（维护放缓）、git-secrets（实质只认 AWS key 模式）。

### 为什么 Censys 的 JARM 值得单独说

JARM 与 JA3 的关键区别：
- **JA3/JA3S 是基于流量被动分析**（服务器面对不同客户端产生不同 JA3S）
- **JARM 是完全主动的**：向 TLS 服务器发送 **10 个精心构造的 ClientHello**（不同 TLS 版本、密码顺序、扩展组合），采集 10 个 ServerHello 后哈希成 **62 字符指纹** —— 前 30 字符是每个 ClientHello 对应的密码与 TLS 版本选择结果（"000" 表示拒绝协商），后 32 字符是累积扩展的截断 SHA256

这套方法之所以有效，是因为 ServerHello 的差异会反映操作系统、OpenSSL 版本、库调用顺序、自定义配置。

## 4.3 为什么 FOFA 在国内资产测绘上被认为更强

三点都有据可查：

**1. 节点与链路优势（最根本的原因）**。国内测绘平台在境内有部署节点和带宽。**从境内节点扫境内 IDC 与从境外扫，路由与回源路径完全不同** —— 境外节点 frequently 被拒绝或拿到不同的 CDN 边缘响应。结果是 FOFA 在国内 IP 段的覆盖密度显著更高。

**2. 指纹库是"中国特色"的**。35 万+ 指纹、13 大类 130+ 子类，其中大量是国产 OA、中间件、小众 CMS、政务/金融系统。Shodan/Censys 的指纹库面向全球主流软件，**这些系统它们认不出来**。

**3. 字段与本地化**。ICP 备案关联、按省份/运营商筛选 —— 这是合规检查和资产台账的刚需，海外平台完全没有这层数据。

**一个概念澄清**：部分第三方文章称"FOFA 自身不主动向目标发包、仅基于已抓取指纹检索"。**综合判断：数据采集由官方扫描节点完成，用户侧为纯索引检索（合规性较好），但平台方是主动扫描方。** 这个区分对判断"我在 FOFA 上查询是否合规"很关键 —— 你在检索已公开索引，与你自己向目标发包探测是两件不同的事。

## 4.4 商业平台溢价到底值不值

### Maltego 图谱分析解决了什么

**先直接回答"数据是不是大半靠第三方 API"：是的。** 官方文档明确其 Graph 通过 **120+ Data Providers、12,000+ 多种检索方法**访问外部数据源，分两类机制：**Data Pass**（官方预装打包数据，按 credit 消耗）+ **Connectors**（100+ 预置连接器，**用你自己的 API key 直连第三方**，费用你承担）。

**图谱分析真正解决的痛点**：OSINT 的瓶颈从来不是"查不到"，而是**关系链断裂**。手工做这件事是：

> 拿到域名 → WHOIS 查注册人 → 反查同邮箱的其他域名 → 查这些域名的证书 → 从 SAN 交叉 → 得到新关联 IP → 重复

Maltego 把这个循环**自动化成 Transforms**，并把每次结果沉淀成可复用的图。手工完成一轮可能需要数小时到数天，图谱分析是分钟级。

**它不可替代的地方不是"查得更全"，而是"把孤立的线索连成可判断的关系网"。**

### 溢价的判断判据

**核心：数据的时间差是硬价值，数据量的堆叠是软价值。**

**值的场景**：
- **凭据泄露的早期预警**（SpyCloud 的 infostealer 日志 → 账号接管预警）。免费工具完全做不到这个时间差
- **持续性威胁狩猎 / 供应链尽调 / 案件调查**（Maltego 的关系图谱复利）

**不值的场景**：
- 只想"知道我在暗网上有没有被提及" → 关键词监控 + 免费泄露库 + 蜜罐能覆盖 80%，不需要 $20K/年
- **TPRM 类**：一次性评估几个供应商 → SecurityScorecard 免费层 + 手工查 ICP/裁判文书足够

**一条务实路径 —— 先用开源组合跑通工作流，量化"每月真正需要多少次商业数据查询"，再决定买不买**：

```
资产发现：  FOFA 免费层（国内）+ Censys Community（250查询/月，全球）
证书/子域： crt.sh + SecurityTrails 免费层
代码泄露：  grep.app + Gitleaks（防护）+ TruffleHog（验证）
历史 URL：  gau（Wayback + Common Crawl + OTX + URLScan）
图谱：      Maltego Basic（200 credits/月，够验证工作流）
工商：      GSXT 官网（免费）+ 天眼查/企查查免费层
```

多数团队会发现**商业查询的实际频次远低于直觉**。

**⚠️ 一个必须避开的选型陷阱**：SecurityScorecard / UpGuard / Black Kite / Panorays **互相做 SEO 竞品对比页**，那些带 AI 生成标注的对比表明确写着"价格区间为分析师估算"。**这类内容用于选型不可靠。**

## 4.5 2026 年四个趋势

**趋势 1：AI/ML 从"辅助"变成"引擎"** —— 但行业内部并非一致看好。
- Censys 的 Predictive Scanning 已是主力（40%+ 新发现服务）；Censys 上线 Natural Language Search + AI Assistant；FOFA 各付费档带 FOFA AI+；ZoomEye 内置 ZoomEyeGPT
- 反对声音同样有分量：Transcend 的 Cardwell 明确说"**AI 不是银弹**，它最有价值的是持续暴露敏感数据在哪，而不是一年一次审计"；CybaVerse CTO 指出**防御方与攻击方都能用 AI 找暴露面**，胜负手在于上下文理解
- **实战建议：把 AI 当噪声削减器（去重、分组、排序），别当发现器。**

**趋势 2：OSINT 与 ASM 深度融合**。Censys 官方定位已从"搜索"转为 "Internet Map + ASM 平台"。Palo Alto 的 ASM 对比指出核心区分点：**ASM 从外部看，映射的是攻击者能看到什么，而不是你的内部记录声称拥有什么**；三类失败场景最值得投入 —— **并购（继承整套攻击面）、云迁移（新实例先上线后入册）、品牌重命名与域名变更（旧营销子域长期留在 DNS）**。

**判断：独立 OSINT 搜索平台的形态正在被 ASM 平台吸收。纯搜索作为"数据源"存在，价值上升；作为"采购标的"，价值下降。**

**趋势 3：暗网监控的卖点从"提及"转向"凭据有效性"**。传统暗网监控的价值是"我知道有人在论坛提到我"—— 价值可疑。新一代（SpyCloud 为代表）的价值是"**我员工的 infostealer 日志里有这条 session cookie，现在还活着**"—— 这是可直接触发动作的（强制下线会话、强制改密、阻断 C2），而不是报告里的一行字。

**趋势 4：代码泄露监控从"加分项"变成"标配"**。三个信号叠加：GitHub 把 Secret Protection 独立成产品线（$19/活跃提交者/月）、TruffleHog 的 live verification 成为默认推荐路径、detect-secrets 维护放缓。

## 5.2 邮箱发现与验证的原理（攻击面与防守面）

### 验证四层

1. **语法校验**
2. **MX 记录**（含 RFC 7505 的 Null MX）→ 抓域级拼写错误（`@gmial.com`）
3. **SMTP RCPT TO 探测**：完整握手 `EHLO → STARTTLS → MAIL FROM → RCPT TO → QUIT`，**从不发送 DATA**。`250`=接受 / `550`=不存在 / `450`=灰名单
4. 风险画像：一次性邮箱、角色账号、**catch-all 域**、垃圾陷阱

**准确率参考**【三方，方向一致但具体数字未验证】：仅语法 ~70% → 仅 MX ~85% → SMTP 握手 ~96% → SMTP+catch-all+风险库 ~98%。

### catch-all 是准确率黑洞

域配置为接受任意 local-part，任何探测都回 250。**标准检测法：先用随机假地址探测，若也回 250 则该域所有 250 结果不可信。**

占比数据两个来源冲突（一说 15-20%，一说 30-40%）—— **建议用自己客户的样本实测，不要采信任何百分比**。倾向认为真实值更高且随企业规模上升，Exchange / Google Workspace 是重灾区。

### ⭐ 邮箱验证的对抗特征（攻防两端都必须懂）

**SMTP RCPT TO 探测在本质上是"目录收割攻击"（Directory Harvest Attack）的协议层机制。**

**扫描特征**：单连接内连续发出数十个 RCPT TO、收件人呈字典序/字母序、`MAIL FROM` 为空或一次性地址、来源集中在少数 IP、**几乎从不进入 DATA 阶段**。合法发信人绝不会连续撞几十个不存在地址。

**防守方应立即做的四件事**：
- **归一化响应**：有效与无效收件人的响应码、措辞、**时延**必须不可区分 —— 枚举之所以成立，就是因为两者长得不一样
- **速率限制 + tarpit 延迟**，让大规模探测在经济上不划算
- 收件人存在性校验本身必须走统一路径，不得产生逐收件人的时延差
- 按来源信誉在 RCPT 之前早期拒绝

**枚举方的成本**：Gmail 约允许单 IP 每小时 200 次 RCPT TO，超出即灰名单；持续探测会进 Spamhaus PBL、Barracuda 等 RBL，**污染的是你的出口 IP 声誉，数周无法恢复**；Yahoo / AOL 存在"假 250"（RCPT TO 回 250，实际发送时才 5xx 弹回）。

**结论：大规模自建 SMTP 验证基础设施在 5 万封/月量级以下是负收益。** 这就是 Hunter / ZeroBounce / Bouncer 这类服务的商业逻辑。

## 5.3 凭据泄露监控：五种检测引擎的原理对比

| 工具 | 引擎原理 | **联网验证** | 输出 |
|---|---|---|---|
| **Gitleaks** | TOML 规则：正则 + **entropy 阈值** + keywords + path + allowlist | ❌ 无 | JSON/CSV/JUnit/**SARIF**；`.gitleaksignore` 按 fingerprint 抑制 |
| **TruffleHog** | 800+ typed detector + 可选**调厂商 API 实测凭据是否存活** | ✅ **有**，输出 `verified`/`unverified`/`unknown` 三态 | Human/JSON/GHA；`--fail` 命中返回 183 |
| **detect-secrets** | 插件池（正则/熵/关键词）+ **baseline 差分模型** | ❌ 无 | baseline 增量 |
| **gitrob / shhgit** | 早期基于敏感文件路径 + 正则，**现已基本被取代** | ❌ | — |
| **GitHub Secret Scanning** | 云端高置信度厂商模式匹配 + partner validity check；push protection **在密钥进入历史前阻断推送** | ✅ 合作方校验 | — |

### 架构本质差异（这一节的洞察）

- **正则** → 覆盖窄但零误报，漏报多
- **entropy** → 覆盖宽，能发现没见过的厂商格式，但**把 UUID / 内容哈希 / 测试 fixture 也当密钥**（熵路线的结构性缺陷）
- **GitHub 云端模式匹配** → 只打高置信度厂商模式，**所以它同时最安全（零误报）和最不安全（完全漏掉内部格式与通用密钥）**
- **TruffleHog 的 live verification** → **这是真正改变分诊数学的那一个**。"AWS key, verified active" 是事故；"verification failed" 是清理任务。**一个比特决定是否呼叫值班。**

### 实测噪音对照【三方，2026-04】

| 工具 | 检出（60 个真实格式密钥） | 误报（15 个熵陷阱） |
|---|---|---|
| TruffleHog | 54 | **2** |
| Gitleaks | 51 | 4 |
| GitHub secret scanning + push protection | 46 | **0** |
| detect-secrets | 39 | 7 |

**漏报高度聚集在两类**：(a) 各工具缺少对应 provider 模式的特定格式；(b) **字符串拼接后跨行的密钥** —— 只有 TruffleHog 部分捕捉到（5 个中 3 个）。

**噪音的本质不是工具不好，是没有基线。** 用 detect-secrets 的 baseline 模型或 Gitleaks 的 `.gitleaksignore`，把"新引入的凭据"与"历史包袱"分开 —— 这一步做好，噪音问题基本消失。

### 推荐分层部署

```
① GitHub push protection（免费，公共库免费）—— 阻断层
        ↓
② Gitleaks 作 pre-commit + CI 门禁
   （--log-opts="origin/main.." 控制在 2 秒内）
        ↓
③ TruffleHog 定期全历史扫描 + 验证 —— 分诊层
        ↓
④ 制定会话吊销预案 ← 最容易被漏掉的一步
```

**单点部署是踩坑主要原因。**

⚠️ **TruffleHog 的代价**：全量历史扫描比 Gitleaks **慢 5–10 倍**；**你的疑似密钥会被发送到外部厂商 API**（开源可审计，但企业合规上仍需安全团队签字 —— 有些团队正因为这一点放弃 TruffleHog，改用 Gitleaks + 人工 review）。

## 5.4 Have I Been Pwned 的隐私机制（很多人没讲清）

**机制**：客户端本地计算密码 SHA-1，**只发送前 5 位 prefix**，API 返回该前缀下**全部后缀 + 出现次数**，客户端本地比对。

```
完整 SHA-1：21BD10018A45C4D1DEF81644B54AB7F969B88D65
前缀：      21BD1          ← 只发送这个
后缀：      0018A45C4D1DEF81644B54AB7F969B88D65
请求：      GET https://api.pwnedpasswords.com/range/21BD1
```

**为什么必然返回 200**：5 位十六进制 = 16^5 = **1,048,576 个桶**，任一有效前缀几乎必然命中数据。

**Add-Padding 头（关键隐私机制）**：未启用时，不同前缀返回的记录条数不同 → **攻击者可通过响应大小/行数反推被查询的是哪个前缀**。启用后随机填充到约 800-1000 条，填充项形如 `00000...0000:0`，客户端直接丢弃。

**⚠️ 必须讲清的边界（官方明确说明）**：
- **`Add-Padding` 不让请求本身匿名**。服务端仍能看到 5 位前缀，它隐藏的只是**响应规模这一侧信道**
- **不要在用户每输入一个字符时发起查询** —— 连续增量请求会泄露正在输入的密码。应在字段失焦或提交时查询

## 5.5 stealer log：比密码清单更重要的东西

### 两种泄露数据的本质区别

| | Breach dump | **Stealer log** |
|---|---|---|
| 来源 | "某一个被攻破的服务" | "某一台被 infostealer 感染的机器" |
| 字段 | `email:password` | 密码 + **session cookie** + 自动填充（姓名/地址/电话/信用卡）+ 加密钱包 + 已装软件 + 屏幕分辨率 + **受害者 IP** + **浏览历史** |
| 密码形式 | 常常是 hash | **明文**（无需破解即可直接使用） |
| 时效性 | 差（改密码即失效） | 新 |

**因此一个 stealer log 能回答密码清单回答不了的问题**：
1. 这台是公司设备还是个人设备？（决定是终端问题还是影子 IT 问题）
2. **有效 session cookie 是否存在？若有，改密码无效 —— 必须吊销会话，否则攻击者直接绕过 MFA。** ← 这是最被低估的事实
3. 感染向量是什么？（盗版软件/恶意广告/假安装包 → 判定这是一个人的疏忽还是针对你组织的攻击）
4. 浏览历史里有哪些内部 URL？（攻击者已经知道你的内部系统结构）

## 5.7 ⭐ LLM 让 OSINT 变强了还是变弱了

**结论：采集与分诊变强了，验证与结论可靠性显著变弱了。**

| 环节 | 方向 | 证据强度 |
|---|---|---|
| 采集指引、查询生成 | **强** | 74 研究综述共识 |
| 海量数据初筛、格式转换、摘要 | **强** | 强共识 |
| 报告起草 | **强** | 强共识 |
| 实体识别（NER） | **弱于专用基线 25%** | 学术实测 |
| **视觉核验** | **严重弱**（280 问仅 14 全对） | Tow Centre 实测 |
| **实时/突发信息** | **严重弱**（35% 重复假信息，拒答率归零） | NewsGuard 实测 |
| **身份归属、责任认定** | **不可用**（对抗提示下强行构建叙事） | ECCWS 2026 |

### 关键证据

**【已查证/学术】arXiv:2607.03233**（74 项研究的系统综述，2026-07-02 收稿）—— 核心发现是**"幻觉-验证鸿沟"**：
- 20+ 项研究把幻觉列为 OSINT-AI 首要可靠性威胁
- 但**全语料库中只有一个 OSINT 专用系统实测了端到端幻觉率**：一个 RAG 架构报告 4%，且条件"有利、不可复现"、数据集私有
- **没有任何论文实证了对抗鲁棒性、端到端验证或有效治理**
- **智能体系统全部只在良性（非对抗）条件下评测**
- 结论明确：**"分析师在环 / copilot 架构"是唯一可辩护的近期部署形态**

**【已查证/媒体】NewsGuard 审计（2025-08）**：主流 LLM **35% 的时间重复虚假信息**（2024-08 为 18%）。**增长原因恰恰是转向实时网页搜索** —— 拒答率从 31% 跌至接近 0，**模型从"不知道"变成"自信地编"**。案例：摩尔多瓦议会选举的虚假信息，多个模型持续从已被欧盟制裁的亲克里姆林宫网络取材。

**【已查证/媒体】Tow Centre**：要求 7 个 AI 系统识别新闻照片的地点、日期、来源 —— **280 个问题中仅 14 个完全正确**。

**根本原因**：LLM 让**生成**变便宜了，但没有让**验证**变便宜。OSINT 的价值 100% 建立在"这条证据是真的"上，而 LLM 不提供这一点。

> **拒答率从 31% 跌到接近 0 这个数字，比 18%→35% 的虚假率上升更值得警惕 —— 一个"不知道"的模型是安全的，一个"自信地编"的模型不是。**

### 域内落地强制三条

1. **多模型交叉验证**（不同厂商的幻觉谱系不同，可互相证伪）
2. **每条结论必须能回溯到原始证据 URL + 抓取时间戳**
3. **保留人工署名与复核记录**

## 5.8 Google Dork：2026 年必须知道的语法变更

### ⚠️ 已废弃的算子（大量教程仍在教这些）

|---|---|

| `link:` | 2017 |

| `daterange:` / `~`（同义词）/ `+`（强制包含） | 2013 / 2013 / 2011 |

### 2026 年可靠工作的算子（简表）

**布尔层**：`"精确短语"`、`-排除`、`OR`（**必须大写**）、`*` 通配符、`()` 分组、`AROUND(N)`（**必须大写**）

### 两个最容易踩的语法坑

- 算子名大小写不敏感，但 **`OR` 和 `AROUND(N)` 只认大写**

### 实用技巧

- **`udm=14` URL 参数强制经典网页结果视图、剥离 AI Overviews** —— AI 时代做 dork 的实用技巧
- **用无痕窗口或登出 Google** 做客观调研（登录态会污染 SERP）

| 算子 | Google | Bing | Baidu | Yandex |
|---|---|---|---|---|
| `filetype:` | ✅ | ✅ `filetype:` | ⚠️ **支持不稳定** | ✅ |
| `intext:` | ✅ | ✅ | ⚠️ **不可靠** | ✅ |
| `link:` / `cache:` | ❌ 已废 | ⚠️ `linkfromdomain` 可用 | — | — |
| 站点特有 | — | `language:` `loc:` `ip:` | `bd:`（站内） | `lr:` |

**中文语料的实际检索应主要依赖 Bing + 站点站内搜索**，Baidu 对 filetype/intext 支持最差、索引质量也低。**Amass 是少数原生支持 Baidu 抓取的开源框架之一** —— 做中国目标资产发现时，Baidu 通道是唯一的一手中文语料入口。

### 防守方自查清单（仅对自己授权的资产执行）

1. **代码仓库**：`.git/`、`.svn/`、`.hg/` 禁止暴露到 web 根目录（部署时 `rm -rf .git` 不够，必须有 CI 校验）
2. **配置文件**：`.env`、`config.php`、`wp-config.php.bak`、`settings.py.bak` 移出 web 根
3. **备份文件**：`.bak .old .orig .save .swp ~ .zip .tar.gz .sql` —— 建立自动化定期 dork 自己域名
4. **目录列表**：Apache `Options -Indexes`、Nginx `autoindex off`
5. **云存储**：S3 / Azure Blob / DigitalOcean 容器 ACL 审计
6. **证书透明度**：CT 日志是**双向的** —— 你能 dork 到别人，别人也能 dork 到你
7. **员工信息**：**无法禁止 dork，只能降低价值** —— 邮箱命名格式一旦泄露，全员邮箱可被算法批量枚举，**且不需要任何人去 dork**。最有效的缓解是 **catch-all 阻断**（但会破坏邮件系统的错误发现能力，需权衡）

**核心洞察：应用下线功能时常常不删除后端逻辑。** 一个 18 个月前"移除"的 `/admin/export` 端点可能仍返回 200 —— URL 只是不再被任何地方链接了。老的 JS 文件在 CDN 上能放很多年。**这些都是活的攻击面。**

⚠️ **合规红线**：历史 URL 挖掘出的已下线端点，**如果现在还返回 200，属于活的攻击面**。用 httpx 批量验证这些历史 URL，性质上是对第三方目标发起主动探测 —— 必须有明确授权。gau 官方文档自己也强调"仅用于授权域名"。

# 第六部分：合规红线（务必读完）

> ⚠️ 以下为一般性合规提示，不构成法律意见。涉及具体业务请咨询执业律师。

## 6.1 核心分界线：查询 ≠ 使用

**查询公开索引数据本身**（Shodan/FOFA 上检索已收录的 banner、证书、工商信息）通常不构成违法。**但对查询结果采取行动 —— 主动探测、尝试登录、获取数据 —— 性质立刻改变。**

## 6.2 中国法律的三条硬线

### 刑法第 285 条（非法侵入计算机信息系统罪等）

**第 2 款**（非法获取计算机信息系统数据、非法控制计算机信息系统罪）：违反国家规定侵入计算机信息系统或采用其他技术手段获取其存储、处理、传输的数据，**情节严重的，处 3 年以下有期徒刑或拘役，并处或单处罚金；情节特别严重的，处 3 年以上 7 年以下有期徒刑，并处罚金**。

**"情节严重"的司法认定标准**（两高《关于办理危害计算机信息系统安全刑事案件应用法律若干问题的解释》第 1 条）：

| 标准 | 门槛 |
|---|---|
| 获取支付结算/证券/期货等**网络金融服务**身份认证信息 | **10 组以上** |
| 获取其他**身份认证信息** | **500 组以上** |
| 非法控制计算机信息系统 | **20 台以上** |
| 违法所得 | **5,000 元以上**或经济损失 **1 万元以上** |

⚠️ **注意这个门槛远低于很多工具的默认行为** —— 一次 `naabu -p-` 对一个 /16 打全端口，就可能越过"20 台"这条线。

**第 3 款（提供侵入、非法控制计算机信息系统程序、工具罪）**：**开发或销售"用于"扫描/攻击的工具，即使未实际攻击也可能构成犯罪。**

### 侵犯公民个人信息罪（第 253 条之一）

**非法获取/出售个人信息 50 条以上即可入刑。** 另有案例：使用爬虫窃取快递公司客户信息并出售，法院认定情节特别严重，判处**有期徒刑五年 + 罚金 100 万元**。

### 个人信息保护法（PIPL）—— 最容易被忽视的境外合规

| 条文 | 内容 |
|---|---|
| **第 3 条** | 境外处理境内自然人个人信息，**以向境内自然人提供产品或服务为目的**、**分析评估境内自然人行为**的，**同样适用本法** |
| **第 10 条** | 任何组织、个人**不得非法收集、使用、加工、传输**他人个人信息，**不得非法买卖、提供或者公开** |
| **第 13 条** | 七项合法性基础。**第 (六) 项"在合理范围内处理个人自行公开或已合法公开的个人信息"是唯一可能的出口** |
| **第 27 条** | 处理已公开个人信息，**个人明确拒绝的除外**；对个人权益有重大影响的，**仍须取得同意** |
| **第 38-39 条** | 跨境提供须满足安全评估/认证/标准合同三选一，且须**取得单独同意** |
| **第 66 条罚则** | 最高**五千万元以下或上一年度营业额 5% 以下**罚款，可责令暂停业务、吊销营业执照 |

**这是本报告最重要的 PIPL 结论**：
- **PIPL 第 3 条的"分析、评估境内自然人行为"条款，比 GDPR 更宽**。GDPR 需要 "establishments" 或定向活动才管辖；PIPL 只要**以境内人为服务目的**或**分析评估其行为**就管辖。**用 Hunter.io 批量分析中国员工邮箱的可投递性，PIPL 项下没有豁免。**
- 用 Apollo/ZoomInfo/Lusha 采购境外数据 broker 的中国员工通讯录，若用于商业触达或任何非"合理范围"，同时踩中第 27 条 + 跨境提供第 38/39 条
- 邮箱+姓名的组合在 PIPL 下**未列入第 28 条敏感个人信息**，但"行踪轨迹"是。社工库里的 `host+user+domain+password` 明文组合属于**非公开的个人信息，无任何合法性基础**

**境外判例已确立的边界 —— Lusha 被意大利 Garante 罚款 200 万欧元**，裁判要点值得逐条抄给法务：
- "B2B 商业数据"**依然是个人数据**，不因商业目的而脱敏
- "数据已公开可见"（如 LinkedIn 资料页）**不等于**第三方可商业再利用的授权
- 持续更新数据主体的在职状态构成 GDPR Art.3(2)(b) 意义上的**行为监测**
- **正当利益（Legitimate Interest）不能支撑**为第三方自身营销/销售/招聘目的提供联系方式数据 —— **这需要同意**
- Lusha 的 LIA（利益平衡评估）被认定"实质上不存在"

## 6.4 三个更重的刑事风险

- **提供侵入工具案**（任城区检察院）：以 7,500 元购买定制爬虫程序，用于获取其他工号权限内的宽带工单信息 **70 余万组** → 两名被告人各获**有期徒刑六个月 + 罚金 1 万元**
- **侵犯公民个人信息罪**：爬虫窃取快递客户信息出售 → **有期徒刑五年 + 罚金 100 万元**
- **非法使用爬虫插件案**（泰州姜堰）：发布"秒传链接提取"及爬虫插件并获利 13,421.59 元 → 认定"提供专门用于从事危害网络安全活动的程序、工具" → 没收违法所得 + **行政拘留三日**

## 6.5 三条容易被忽视的执法要点

**1. AI 不给你免责。** 已有明确案例：公安机关办案时明确认定 **"AI 作为工具，不改变违法行为的法律性质"**。试图以"代码系 AI 生成""不了解技术原理""仅作测试"为由推诿，**均无法规避法律制裁**。公安机关会固定攻击脚本、网络日志、API 调用记录、目标 IP 清单及数据提取痕迹作为证据。

**2. "一案双查"机制**（2018 年起全面实行）：查员工泄露数据时**同步检查企业是否履行网络安全义务**，企业独立面临行政处罚。双重处罚依据：《数据安全法》第 45 条、PIPL 罚则。

**3. 行政拘留 → 判刑之间看是否达到"情节严重"。** 有一起案例的裁量思路值得注意：某行为人利用系统漏洞获取他人设备数据，造成服务器网络堵塞、无法正常访问，已有现实危害。公安机关认定违反《网络安全法》第 29 条，**适用《治安管理处罚法》第 33 条给予行政拘留** —— 理由是虽造成现实危害，但**尚未达到刑事追诉的裁量标准**。这条给出了重要的裁量参照。

## 6.6 给安全从业者的操作清单（可直接贴在墙上）

1. **只查自己或已获书面授权的资产** —— 授权范围应明确包含"主动探测"。**主动 SMTP 探测应单独书面授权。**
2. **保留查询审计记录** —— 注明时间、目的、授权来源。**企业法务可能对员工查询竞品 IP 段有异议**，即使查询本身合法
3. **发现暴露资产走规范披露渠道** —— 走 security.txt、厂商 SRC 或本国 CSIRT，**不要直接"顺手测一下"**
4. **发现泄露凭据立即上报，不使用** —— **拿到了不等于可以用**；使用泄露凭据访问系统是最容易被认定为"情节严重"的行为
5. **漏洞奖金项目也要守边界** —— HackerOne/Bugcrowd 上活跃的赏金项目**明确禁止超出"横幅读取范围"的测试**
6. **云环境特别危险** —— 公有云上存在大量**不属于你的**实例。**用 naabu 的 ASN 输入前务必确认该 ASN 内所有 IP 的归属**
7. **不要以"AI 生成的""开源工具""仅供学习"为抗辩理由**
8. **员工数据采购是"共同风险"** —— Lusha 案的关键教训：**罚款落在供应商，但合规风险同样落在不知情的采购方**。DPO/法务必须在采购前介入审查数据来源合法性

**⛔ 一条禁止性建议：不要为了"验证一下"而跑 SMTP 枚举。** 用 Hunter 这类合规的规模化服务，或只做被动查询。这条线的法律风险收益比极差。

## 7.2 三个推荐的组合工作流

### 工作流 A：国内政企资产盘点（等保/攻击面梳理）

```bash
# 阶段 1：被动发现（合规风险最低）
subfinder -d target.com -all -o subs.txt          # 纯被动，不对目标发包
uncover -q "domain:target.com" -e fofa,hunter,quake  # 多引擎交叉

# 阶段 2：证书层梳理
tlsx -l subs.txt -san -cn -so -resp-only            # SAN/证书链
echo target.com | crtsh                           # 免费的 CT 日志

# 阶段 3：主动探测（⚠️ 需书面授权）
naabu -l subs.txt -p top-1000 -exclude-cdn -rate 1000
httpx -l urls.txt -sc -title -tech-detect -favicon
                  # -sc 状态码 -title 标题 -tech-detect 技术栈
                  # ⚠️ favicon/JARM 默认关闭，需显式加

# 阶段 4：交叉验证（关键！对抗 SYN Proxy 误报）
nmap -sT -sV -p <从 naabu 筛出的高价值端口>     # 完整连接扫描
nuclei -l urls.txt -severity low,medium,high -rl 200

# 阶段 5：备案与归属
# 手工查 ICP 备案（ICP 备案号查询）+ 天眼查/企查查免费层
```

**⚠️ 阶段 4 是最容易被跳过、但最值钱的一步。** 不做交叉验证，你的报告里会全是 SYN Proxy 造成的误报。

### 工作流 B：凭据泄露专项排查

```bash
# 1. 仓库历史全量扫描 + 验证（最慢但最有价值）
trufflehog git file://. --all-commits --only-verified
                       # --only-verified 只报确认存活的
                       # ⚠️ 慢 5-10 倍；疑似密钥会发到外部厂商 API

# 2. CI 门禁（秒级反馈）
gitleaks detect --log-opts="origin/main..HEAD"   # 限定范围控在 2 秒内
gitleaks git . --redact

# 3. 建立基线，抑制历史包袱
# Gitleaks: .gitleaksignore 按 fingerprint 抑制（记录能跨 rebase 存活）
# detect-secrets: .secrets.baseline

# 4. 员工侧 stealer log（Hudson Rock 免费层，3 域名）
#    ⚠️ 拿到结果后 → 立即上报，不要使用；确认有效 session cookie → 吊销会话（改密码无效）
```

### 工作流 C：历史资产挖掘

```bash
# 1. 多源历史 URL 聚合（比 waybackurls 单独使用覆盖面强得多）
gau target.com --subs
gau target.com --providers wayback,commoncrawl   # 可复现、可排障
gau target.com --from 202201 --to 202212 --fp    # 限定时间窗

# 2. 筛出敏感扩展名
gau target.com | grep -E "\.(php|asp|aspx|jsp|json|env|sql|bak|log|config)$"

# 3. ⚠️ 验证这些 URL 是否还活着 —— 这一步是主动探测，需授权
httpx -l filtered_urls.txt -sc -mc 200
# 找仍返回 200 的已下线端点 = 活的攻击面
```

## 7.4 必须先建的两个能力（常被跳过）

**1. 邮件系统的 catch-all 与响应归一化审计。** 这是唯一一个"同时提升安全性并消除最大攻击信标"的动作。catch-all 让 SMTP 探测无法区分邮箱存在性；响应归一化让枚举在协议层失效。

**2. 授权流程与资产台账。** 主动扫描前必须有书面授权（含目标 IP/CIDR、允许的协议端口、允许的时间窗、**允许的扫描类型**）。资产台账要记录"哪些是授权的"—— 蓝队在生产环境做全量 SYN 扫描会触发自家安全团队告警，**这是授权流程要解决的事，不是技术问题**。

# 第八部分：必须避开的六个坑

## 坑 1：把"AI 识别准确率"写进方案

httpx 的技术栈识别是**基于 Wappalyzer 的规则匹配**，favicon hash 是**确定性哈希**。检索到的"85-90% 准确率"全是反欺诈/设备指纹领域的厂商营销内容，与资产测绘无关。**目前可查证、可落地的仍是规则+哈希。** ML 在资产测绘侧的真实位置是 nuclei 的语义匹配（用于漏洞响应内容判定）。

**唯一真实的 2026 ML 动向**：nuclei v3 的 `-llm` 语义匹配，支持本地 ollama/llamacpp/vllm（数据不出境）。这是可以写进方案的，但要描述准确。

## 坑 2：把 SEO 竞品对比页的价格当依据

SecurityScorecard / UpGuard / Black Kite / Panorays 互相做对比页，那些带 AI 生成标注的价格区间（$29K/$50K 等）**明确写着是分析师估算**。TPRM 类只有 UpGuard 价格相对透明。

## 坑 3：忽略 FOFA/Hunter 免费版不可商用

**FOFA 免费/个人/专业版均不可商用**（免费层仅非商业）。用免费层数据做正式商业交付是合规风险。

## 坑 4：用免费层数据下结论

- **ZoomEye 免费层无 API** —— 等于无法接入任何自动化流程
- **Intelligence X 免费层看不到 leaks 和 stealer logs 这两类最有价值的数据桶**
- **LeakIX 免费层结果延迟 15-30 天** —— 对应急响应致命
- **天眼查/企查查免费层无法完成任何一次供应商核实**（缺 UBO、年报、完整裁判文书）
- **Censys 免费层只 250 查询/月**，且【存疑】API 已收紧

## 坑 5：以为 Shodan favicon hash 是 MD5

是 **MurmurHash3 x86_32 + RFC 2045 每 76 字符换行的 Base64 + 有符号整数**。这条被无数中文教程抄错，导致自建工具算出的 hash 永远对不上。

## 坑 6：没有做交叉验证就把扫描结果当结论

三个高频误报源：
1. **SYN Proxy**（AWS Global Accelerator / 各类 DDoS 防护）→ 用 `-sT -sV` 交叉验证
2. **云上主机全显示 down** → 加 `-Pn`
3. **防火墙 RST rate limiting** → 交叉验证

**扫描给你的是"从互联网视角可达什么"，不是"主机上真实监听什么"。** 这条应写进任何资产梳理报告的方法论章节。

## 一句话收尾

**信息收集这个领域，2026 年最大的变化不是工具变强了，而是"验证"和"分诊"成了瓶颈。** 采集能力已经过剩（免费的能拿到过去商业情报平台才能拿的东西），但：
- 指纹识别的误报是**哈希的数学性质**，不是模型精度问题
- 凭据监控的噪音是**基线治理问题**，不是工具问题
- LLM 带来的最大风险不是虚构，是**"自信地编"**（拒答率从 31% 跌到接近 0）

所以真正要投入的，不是再多一个工具，是**分诊能力 + 基线治理 + 证据回溯链**。
